GO sous réserve

Aucune vulnérabilité critique ou élevée connue ne reste ouverte, et les 438 tests des deux dépôts passent après corrections. Mais deux réserves bloquent un GO franc, et aucune des deux ne se lève depuis cet environnement :

1. La correction la plus importante (en-têtes de sécurité et HTTPS sur le dashboard) est une configuration nginx qui n'a pu être ni validée syntaxiquement ni appliquée ici — nginx n'est pas disponible dans cet environnement et le VPS n'est pas accessible. 2. 01  État initial

Le dépôt Yobante contient quatre projets. L'audit porte sur yobante-admin (le dashboard) et, parce que c'est là que les autorisations sont réellement appliquées, sur yobante-boutique-back (l'API qu'il consomme). yobante-boutique-mobile (Flutter) et yobante-colis-backend n'ont été lus que pour vérifier des contrats d'API.

Architecture constatée

  • Dashboard — SPA React 19 + TypeScript, Vite 8, Tailwind 3, TanStack Query, Zustand (persisté), react-router 6. 128 fichiers sources, ~40 routes. Servi en statique par nginx sur admin.yobante-boutique.com, déployé par GitHub Actions (scp du dist/).
  • API — Express 4 / Sequelize 6 / PostgreSQL, 268 fichiers. Authentification JWT (access 1 h + refresh 7 j avec rotation et stockage haché en base), bcrypt coût 12, Helmet, CORS en liste blanche, express-rate-limit, Winston, Joi.
  • Modèle d'autorisation — trois rôles : ADMIN, VENDEUR, CLIENT. Tout /api/v1/admin/* est protégé au point de montage dans src/app.js par la chaîne auth → motDePasseChange → adminMiddleware. C'est une bonne décision de conception : aucune route admin ne peut être ajoutée sans garde, et l'audit n'a trouvé aucune route admin non protégée.

Ce qui était déjà solide

Il faut le dire clairement, parce que cela a orienté l'audit vers les vraies zones de risque : le projet n'est pas un prototype. La vérification de session côté serveur existe (GET /admin/me derrière le middleware ADMIN, re-contrôlée au retour d'onglet), les refresh tokens sont hachés en base et tournés à chaque rafraîchissement, le rejeu d'un jeton révoqué est détectable (révocation plutôt que suppression), l'énumération de comptes est évitée sur le parcours de réinitialisation, les secrets JWT sont validés au démarrage (présence et distinction mutuelle), CORS=* est rejeté par construction, et aucun secret n'est suivi par git dans les deux dépôts. L'API portait déjà 278 tests, dont 101 dédiés au contrôle d'accès admin.

02  Constats

Classés par gravité. Chaque entrée donne l'emplacement, le scénario de reproduction, l'impact réel et la correction appliquée.

P0

Le dashboard était servi sans aucun en-tête de sécurité, et en HTTP

deploy/nginx-admin.yobante-boutique.com.conf

Corrigé La configuration nginx du dashboard ne déclarait aucun en-tête de sécurité — pas de CSP, pas de HSTS, pas de X-Frame-Options, pas de nosniff — et n'écoutait que sur le port 80, sans redirection vers HTTPS.

L'impact est double. D'abord, les jetons d'administration vivent dans le localStorage (choix d'architecture, voir le constat P2 correspondant) : sans CSP, toute exécution de script tiers dans la page équivaut à une prise de contrôle complète du compte administrateur. La CSP est précisément le contrôle compensatoire qui manquait. Ensuite, sans redirection HTTPS ni HSTS, un accès à http://admin… transmet identifiants et jetons en clair, et reste exploitable par SSL-stripping.

Le contraste avec l'API est frappant et a servi de référence : yobante-boutique-back/deploy/nginx.conf est, lui, correctement durci (HSTS, nosniff, Referrer-Policy, TLS 1.2+, redirection 301). Le durcissement n'avait simplement jamais été porté sur le dashboard — la cible de plus grande valeur.

Correction : réécriture de la configuration avec bloc HTTPS, redirection 301 depuis HTTP (en préservant le challenge ACME de certbot), TLS aligné sur celui de l'API, et un nouveau fichier deploy/nginx-security-headers.conf contenant CSP, HSTS, frame-ancestors, nosniff, Referrer-Policy et Permissions-Policy.

Détail qui compte. Les en-têtes sont dans un fichier includeé dans chaque bloc location, et non posés une fois au niveau server. Dans nginx, un add_header présent dans un location annule tous ceux hérités du bloc parent : les locations qui posent leur propre Cache-Control (/assets/, index.html) auraient perdu la CSP sans que rien ne le signale.

P1

Cinq connexions depuis une même IP verrouillaient toute l'authentification, rafraîchissement de jeton compris

src/auth/services/auth.service.ts · back: src/middlewares/rateLimit.middleware.js, src/routes/auth.routes.js

Corrigé C'est le défaut le plus intéressant de l'audit, parce qu'il naît de la rencontre de deux décisions correctes prises séparément.

Côté dashboard, chaque connexion émettait deux requêtes en parallèle : /auth/admin/login vers la boutique, et /auth/login vers le « backend colis ». Or VITE_SHIPMENT_API_URL et VITE_SHOP_API_URL pointent sur la même origine (l'API boutique) dans .env, .env.local et .env.example. La seconde requête partait donc sur l'endpoint client de la boutique, avec un corps { email, password } alors que le schéma Joi exige identifiant — et échouait en 400 à chaque connexion, systématiquement.

Côté API, authLimiter est une instance unique partagée par cinq routes (/login, /admin/login, /refresh, /verify-reset-code, /reset-password), plafonnée à 5 requêtes/15 min par IP, en skipSuccessfulRequests — seuls les échecs comptent.

Reproduction : se connecter cinq fois avec succès depuis la même adresse IP publique en moins de quinze minutes. Chaque connexion réussie produisait un échec « gratuit » sur /auth/login ; au cinquième, le compteur partagé atteignait son plafond et tout le périmètre auth répondait 429 — y compris /auth/refresh, ce qui coupait aussi les sessions déjà ouvertes. Un bureau derrière un seul NAT atteignait ce seuil en usage strictement normal.

Correction : la requête colis n'est plus émise si VITE_SHIPMENT_API_URL n'est pas une origine distincte de l'API boutique (colisEstUnServiceDistinct()). La bascule se fera d'elle-même le jour où les deux URL diffèrent, sans changement de code. Le contrat a par ailleurs été corrigé pour correspondre au vrai backend colis ({ email, mot_de_passe } → { token, utilisateur }) : tel qu'écrit, l'appel ne pouvait aboutir sur aucun des deux backends.

P1

L'espace « Colis » affichait des données fabriquées et confirmait des actions qui n'atteignaient jamais le serveur

src/pages/shipment/dashboard/panels/*.tsx · src/app/routes/ColisRoute.tsx

Corrigé Les cinq panneaux de l'espace Colis (OverviewPanel, ColisPanel, ConteneursPanel, ClientsPanel, AdminsPanel) n'effectuent aucun appel API — vérifié : aucun import de client HTTP, ni useQuery, ni useMutation dans tout le dossier. Ils lisent des constantes FAKE_COLIS, FAKE_CLIENTS, FAKE_ADMINS, FAKE_CONTENEURS, FAKE_DATA.

Le problème n'est pas l'affichage de chiffres faux, c'est la classe de bug la plus trompeuse qui existe dans une interface d'administration : l'interface confirme des opérations qui n'ont pas eu lieu. « Valider » et « Refuser » un colis, « Désactiver » et « Supprimer » un client, « Créer » un administrateur, changer un statut — tout ne mute qu'un useState local. Le motif de refus est saisi dans une modale, puis jeté. L'administrateur voit le statut changer, la ligne disparaître, et croit l'opération faite ; elle est perdue au rechargement.

Reproduction : se connecter comme administrateur, saisir /colis/dashboard dans la barre d'adresse, supprimer un client, recharger. PrivateRoute ne contrôlait que l'authentification et le rôle, jamais l'application concernée : la page était donc atteignable par tout administrateur.

Correction : nouvelle garde ColisRoute exigeant une session colis réelle (isShipmentAvailable), ce qui rend l'espace inatteignable tant que le backend colis n'est pas déployé. Le code des panneaux est conservé intact — c'est une fonctionnalité inachevée, pas à supprimer : elle redeviendra accessible d'elle-même le jour où une vraie session colis sera possible. La condition de reprise est documentée dans SETUP.md et dans l'en-tête de ColisRoute.

P1

Le remplacement du mot de passe temporaire ne révoquait aucune session

yobante-boutique-back/src/services/auth.service.js — changerPremierMotDePasse()

Corrigé changePassword() révoque bien tous les refresh tokens de l'utilisateur, dans une transaction. changerPremierMotDePasse(), non : il se contentait d'écrire le nouveau hash, hors transaction.

C'est pourtant le chemin où le risque est le plus élevé. Un mot de passe temporaire est généré par l'administration et transmis hors bande — e-mail, message — donc potentiellement lu par un tiers. Scénario : le tiers se connecte avant le titulaire et obtient un refresh token valide 7 jours. Le titulaire change ensuite son mot de passe, en croyant reprendre le contrôle du compte. Avant correction, la session du tiers survivait intégralement au changement.

Correction : révocation de tous les refresh tokens actifs, dans la même transaction que l'écriture du mot de passe. Couvert par quatre nouveaux tests, dont un qui échoue sur le code d'avant.

P1

Dépendances d'exécution vulnérables, dont une voie XSS

package.json · package-lock.json

Corrigé npm audit remontait 27 vulnérabilités. La distinction qui compte est exécution contre développement : seules 3 touchaient des dépendances livrées au navigateur.

  • axios 1.18.1 — pollution de prototype dans l'adaptateur fetch (GHSA-vh66-26gq-q6x8). → 1.20.0
  • react-router-dom 6.30.4 — redirection ouverte menant à du XSS (GHSA-jjmj-jmhj-qwj2, CVSS 6.9). Sur un dashboard qui garde ses jetons en localStorage, une voie XSS est une voie de compromission de compte. → 6.30.6

Après mise à niveau : 0 vulnérabilité haute ou critique sur les dépendances d'exécution. Les deux avis moyens restants sont traités en section 8 (risques résiduels), analyse d'exploitabilité incluse.

Les 2 critiques (tinypool, vitest) et la majorité des hautes sont des dépendances de développement (vitest, eslint, tailwind, postcss) — absentes du bundle de production. Elles n'ont volontairement pas été mises à niveau : le correctif passe par vitest 4, un changement majeur du lanceur de tests dont le risque de régression dépasse, en pleine préparation de mise en production, celui d'un vecteur qui exige déjà l'exécution de code hostile en local.

P2

Les limiteurs calibrés « par utilisateur » étaient en fait par adresse IP

yobante-boutique-back/src/app.js

Corrigé adminLimiter, authenticatedLimiter et mutationLimiter utilisent keyGenerator: req.user?.id || req.ip, mais étaient tous montés avant le middleware auth : req.user n'existait pas encore, et la clé retombait toujours sur l'IP.

Conséquence pratique : les 200 requêtes/15 min des routes admin étaient partagées par tous les administrateurs d'un même bureau. Une page du dashboard émettant plusieurs requêtes, deux ou trois administrateurs simultanés suffisaient à provoquer des 429 en usage normal.

Correction : auth placé avant le limiteur sur les dix points de montage concernés. Les limiteurs réellement destinés à des routes non authentifiées (callbacks de paiement, formulaire public de suppression de compte) ont été laissés inchangés — leur clé IP y est correcte.

P2

La désactivation d'un compte laissait jusqu'à 30 secondes d'accès complet

yobante-boutique-back/src/services/admin/user.service.js, vendeur.service.js

Corrigé Le middleware d'authentification met en cache le profil { role, isActive } pendant 30 secondes. Le blocage d'un administrateur purgeait bien ce cache, le blocage d'un vendeur aussi — mais desactiverUser(), non. Le compte conservait donc un accès complet pendant la durée du TTL.

C'est l'outil qu'un administrateur utilise face à un compte compromis ou abusif : il doit couper l'accès immédiatement. L'incohérence entre les trois chemins était d'autant plus nette que le motif de purge existait déjà, nommé, dans deux services voisins.

Correction : purge du cache d'authentification sur activation et désactivation, et révocation des refresh tokens dans une transaction — également ajoutée au blocage d'un vendeur. AuthService.refresh refusait déjà un compte inactif, donc rien n'était exploitable dans l'instant ; mais les jetons restaient valides en base et redevenaient utilisables à la réactivation du compte, y compris un jeton volé avant la désactivation.

P2

Documentation OpenAPI exposée publiquement en production

yobante-boutique-back/src/app.js

Corrigé /api-docs (Swagger UI) était monté sans condition, et la route racine / en publiait l'adresse. Toute la surface d'API — chemins admin, schémas de corps de requête, noms de champs — était ainsi offerte à un attaquant, lui épargnant toute phase de découverte.

Correction : servie hors production uniquement, avec réouverture explicite possible via ENABLE_API_DOCS=true (utile en staging) mais jamais par défaut. La route racine n'annonce docs que lorsqu'elle est effectivement servie.

P2

Liste noire de rôles là où une liste blanche était attendue

src/app/routes/PrivateRoute.tsx

Corrigé La garde refusait explicitement VENDEUR et CLIENT : ROLES_SANS_ACCES.includes(role). Tout rôle absent de cette liste — un futur SUPPORT, LIVREUR, GESTIONNAIRE, ou une valeur vide — était donc accepté par défaut.

Aucun de ces rôles n'existe aujourd'hui (le backend n'en déclare que trois), donc le défaut n'était pas exploitable en l'état. Il est classé P2 et non P1 à ce titre : c'est une faille d'omission future, où l'ajout d'un rôle côté API accorde silencieusement l'accès au dashboard.

Correction : inversion en liste blanche — seul ADMIN ouvre le dashboard, via estAdminBoutique() déjà utilisé ailleurs. Couvert par quatre nouveaux cas de test.

P2

Un seul paquet JavaScript de 911 kB pour quarante pages

src/app/routes/index.tsx · src/layouts/*/index.tsx

Corrigé Le build produisait un chunk unique de 911 kB (239 kB gzip), avec l'avertissement de Vite. Ouvrir la page de connexion téléchargeait l'analytique, la finance, la gestion de stock et l'espace colis.

Correction : chargement différé des 36 pages (React.lazy), avec frontière Suspense placée dans les layouts — la barre de navigation reste donc affichée pendant le chargement d'un module, au lieu d'un écran vide. Mesures avant/après en section 6.

P2

Le déploiement en production n'exécutait aucun test

.github/workflows/deploy.yml

Corrigé Le workflow installait, écrivait le .env, construisait et copiait dist/ sur le VPS. Ni tests, ni type-check, ni lint : un commit cassé partait directement en production.

La seule vérification post-déploiement, curl -f -I https://admin…, ne prouve rien d'utile ici : nginx répond 200 sur index.html même avec un bundle défectueux, puisque l'erreur ne se manifeste qu'à l'exécution dans le navigateur.

Correction : étapes type-check et test ajoutées avant le build, bloquantes. Le lint n'a volontairement pas été rendu bloquant — voir le constat P3.

P2

Jetons d'administration en localStorage

src/infrastructure/auth/tokenManager.ts

Résiduel — documenté Les jetons d'accès et de rafraîchissement sont stockés en localStorage, donc lisibles par tout script exécuté dans la page. C'est le constat que l'audit précédent plaçait en tête de ses « corrections immédiates », sans l'appliquer.

Il n'a pas été corrigé ici, et c'est un choix assumé plutôt qu'un oubli. L'API émet déjà le refresh token en cookie HttpOnly / Secure / SameSite=strict en plus du corps de réponse. Mais le dashboard et l'API sont sur des origines différentes (admin. contre api.), et SameSite=strict empêche l'envoi du cookie en cross-site : basculer entièrement sur les cookies demande de revoir le placement des domaines, la politique SameSite et la protection CSRF qui en découle. C'est une migration d'architecture, à mener avec une fenêtre de test, pas un correctif de dernière minute avant déploiement.

Le risque est donc traité par son contrôle compensatoire : la CSP script-src 'self' introduite en P0, plus la suppression de la voie XSS de react-router (P1). À planifier explicitement ; voir section 8.

P3

Libellés de formulaire non reliés à leurs champs

src/pages/shop/profil/ProfilPage.tsx — composant Champ

Corrigé Le composant Champ rendait un <label> sans htmlFor et un <input> sans id. Un lecteur d'écran annonçait « zone de saisie » sans dire laquelle, et cliquer le libellé ne donnait pas le focus — échec WCAG 2.2 AA (1.3.1 et 4.1.2) sur les six champs de la page, dont les trois du changement de mot de passe.

Correction : association via useId(), et autocomplete explicite (current-password, new-password, given-name, family-name, tel) — ce qui permet aussi aux gestionnaires de mots de passe de proposer une génération. LoginPage faisait déjà tout cela correctement ; c'est cette page qui avait dérivé.

P3

Documentation d'exploitation décrivant des routes inexistantes

SETUP.md · security-audit-results.md

Corrigé SETUP.md décrivait un parcours de connexion passant par /select-app, /shop/dashboard et /shipment/dashboard — trois chemins absents du routeur (les vrais sont /login, /boutique/*, /colis/*). Pour quiconque reprend le projet, cette documentation envoie chercher des bugs inexistants.

security-audit-results.md posait un problème plus sérieux : il analysait des fichiers supprimés depuis (LoginForm.tsx, AppSelectGuard.tsx), affirmait des manques déjà couverts (vérification du rôle côté serveur, révocation des refresh tokens), et son « plan d'action en 3 phases » n'avait jamais été appliqué. Un rapport de sécurité faux est pire qu'absent : il donne l'illusion d'une revue faite.

Correction : SETUP.md réécrit sur l'état réel (dont le statut du backend colis et la condition de reprise), et security-audit-results.md préfixé d'un avertissement de péremption renvoyant vers le présent rapport.

P3

208 avertissements de lint, et un script de lint qui échoue

.eslintrc.cjs · package.json

Non corrigé — délibérément npm run lint est configuré avec --max-warnings 0 alors que le projet porte 208 avertissements (207 @typescript-eslint/no-explicit-any, 1 react-refresh/only-export-components). Le script échoue donc toujours, ce qui le rend inutilisable comme garde-fou.

Non corrigé sciemment : typer correctement 207 any est un travail de fond qui touche la quasi-totalité des pages, avec un risque de régression réel et aucun gain de sécurité immédiat. C'est pour cette raison que le lint n'a pas été ajouté comme étape bloquante du déploiement — l'y mettre en l'état aurait bloqué tous les déploiements. Recommandation en section 8.

P3

Code OTP de réinitialisation sans compteur de tentatives

yobante-boutique-back/src/services/auth.service.js — verifyResetCode()

Non corrigé — hors périmètre dashboard Le code à 6 chiffres n'est pas invalidé après N échecs ; le code reconnaît lui-même l'approximation en commentaire. La force brute reste cependant contenue par authLimiter (5 échecs/15 min par IP) face à un espace de 10⁶ dans une fenêtre de 10 minutes : l'attaque n'est réaliste que distribuée sur un grand nombre d'adresses.

Classé P3 et laissé en l'état car ce parcours ne concerne pas les administrateurs : forgotPassword() exclut explicitement les comptes ADMIN. Le corriger touche le parcours client/mobile, hors du périmètre de cet audit. Un compteur de tentatives par enregistrement OTP reste la correction propre.

Contrôles vérifiés comme déjà corrects

Points explicitement contrôlés, trouvés satisfaisants, et laissés inchangés :

  • Autorisation côté serveur — tout /api/v1/admin/* est gardé au point de montage ; aucune route admin sans garde. Vérifié par lecture exhaustive des 19 fichiers de routes admin et par les 101 tests de admin.protection.test.js (dont « jeton CLIENT → 403 » et « jeton ADMIN → passe »).

  • Secrets — aucun fichier .env suivi par git dans les deux dépôts ; secrets de déploiement en GitHub Secrets ; secrets JWT validés au démarrage (présence et distinction mutuelle). Aucun secret n'apparaît dans ce rapport.

Hypothèses posées

  • app.set('trust proxy', 1) suppose exactement un proxy en amont. La configuration nginx auditée correspond ; si une couche supplémentaire est ajoutée (CDN, répartiteur), les limiteurs par IP deviennent contournables par en-tête X-Forwarded-For.
  • La CSP autorise connect-src https://api.yobante-boutique.com. Tout changement de domaine d'API exige de mettre cette directive à jour, sinon le navigateur bloquera toutes les requêtes du dashboard.
  • style-src 'unsafe-inline' est nécessaire et non contournable sans réécriture : l'application utilise massivement l'attribut style={{…}} et sweetalert2 injecte ses styles à l'exécution. script-src reste strict, ce qui est la directive qui protège réellement du XSS.

09  Mise en production

Conditions à lever avant déploiement

  1. Rejouer les tests DB. npx jest au complet sur un environnement doté de PostgreSQL. Les 17 tests ignorés doivent passer.
  2. Valider nginx. Copier deploy/nginx-security-headers.conf vers /etc/nginx/snippets/yobante-admin-security.conf, puis la configuration de site. Vérifier dans cet ordre : le certificat existe (certbot --nginx -d admin.yobante-boutique.com si ce n'est pas le cas), puis nginx -t, puis systemctl reload nginx. La configuration référence les certificats : l'appliquer avant leur émission empêche nginx de démarrer.
  3. Vérifier la CSP sur une page réelle. Ouvrir le dashboard, console navigateur, se connecter et parcourir plusieurs pages. Toute violation CSP y apparaît explicitement. C'est le contrôle qui ne peut pas être simulé : une CSP trop stricte casse l'application silencieusement pour l'utilisateur.

Déploiement

  1. Fusionner sur main — le workflow exécute désormais type-check et tests avant de construire, et s'arrête en cas d'échec.
  2. Côté API, redéployer avec NODE_ENV=production et sans ENABLE_API_DOCS.
  3. Sauvegarde PostgreSQL vérifiée avant toute migration (npm run backup). Aucune migration destructive n'est introduite par cet audit.

Vérifications après déploiement

  1. curl -I https://admin.yobante-boutique.com — confirmer la présence de Content-Security-Policy, Strict-Transport-Security, X-Content-Type-Options. Contrôler aussi /assets/ et /index.html, précisément les emplacements où les en-têtes se perdaient.
  2. curl -I http://admin.yobante-boutique.com — doit renvoyer 301 vers HTTPS.
  3. curl https://api.yobante-boutique.com/api-docs — doit renvoyer 404.
  4. Se connecter six fois de suite depuis la même adresse IP : c'est le test de non-régression du défaut P1 de verrouillage. Avant correction, la sixième tentative échouait en 429.
  5. Saisir /colis/dashboard comme administrateur — doit renvoyer vers /boutique/dashboard.
  6. Créer un compte à mot de passe temporaire, ouvrir une session, changer le mot de passe, puis vérifier que la première session ne peut plus rafraîchir son jeton.

Surveillance

Sur les premières 24 heures : taux de 429 sur /api/v1/auth/* et /api/v1/admin/* (les deux corrections de limiteurs doivent faire chuter ce taux — une hausse signalerait une erreur de configuration de proxy), violations CSP remontées par les administrateurs, taux de 401/403 sur /admin/me, et erreurs 5xx dans les journaux Winston.

Retour arrière

  • Dashboard — redéployer le dist/ précédent (ou git revert puis laisser le workflow reconstruire). Le dashboard est statique : le retour arrière est immédiat et sans état.
  • nginx — conserver une copie de l'ancienne configuration avant remplacement ; la restaurer puis nginx -t && systemctl reload nginx. Attention : une fois HSTS envoyé avec max-age=63072000, les navigateurs refuseront le HTTP en clair pendant deux ans pour ce domaine. Un retour vers une configuration HTTP seule serait donc inopérant pour les visiteurs déjà venus. C'est la seule modification de cet audit qui n'est pas trivialement réversible, et la raison pour laquelle includeSubDomains a été conservé mais preload retiré de l'en-tête.
  • API — pm2 reload sur le commit précédent. Les quatre fichiers modifiés sont sans schéma ni migration ; aucune donnée n'est transformée, le retour arrière est propre.

10  Portée de cet audit

Un audit automatisé ne garantit pas l'absence de vulnérabilités. Ce rapport distingue systématiquement ce qui a été exécuté et vérifié de ce qui n'a pu l'être, et aucun statut GO n'y est accordé sur la seule absence d'erreur visible. Les contrôles listés comme non réalisables — test d'intrusion réel, tests adossés à la base, vérification des en-têtes servis, revue UI/UX et accessibilité en navigateur, comportement sous charge — demandent une intervention humaine sur les environnements concernés avant de pouvoir être considérés comme couverts.
